kv slots is the widest a shared pass can be, so it is the number that says whether continuous batching is on. The shipped default is 1 — a second slot does not fit the graph budget at the shipped chunk, and where it does fit, the concurrency chart below is the measurement of what it buys; aiis-clef, 1 kv slot and 3 kv slots are the same binary with CLEF_KV_SLOTS forced, measured so the choice is a result rather than a claim. At a 131,072-token context, 3 slots need 12,438 MiB of KV against 8,292 for 2, and the 8,192-row graph is refused — the pass then runs eager, which is the cost this table exists to expose. llama.cpp is the row of dashes: its `/health` is `{"status":"ok"}` and nothing else, so its limit is the `-c`/`-ub` on its launch line (38-PERFORMANCE-TUNING.md §68a) rather than a field this table can read. The wall time is the figure of merit, not the sum of the latencies: two requests served one after the other and two served in one shared pass have the same total latency, and only the wall time separates them. N x an arm's own single-request latency is what its wave costs (95-102% of it, every arm) — which is the honest result: at these sizes a second slot buys isolation rather than throughput. A request ends when its own compute is done rather than queueing behind another. The largest rung every arm ran is used, so the comparison is like for like.

At a fixed 4,096-row chunk only the slot count differs, so this is the like-for-like comparison the chart is for. Wall time for the whole wave: 2 slots answers it 62-153 ms sooner — 3,192 against 3,254 ms at two concurrent and 4,736 against 4,889 at three.

The mean tells the other story. At two concurrent the 2-slot arm answers in 3,170 ms mean against the 1-slot arm's 2,442 ms. Same work, different queueing: with two slots both requests are slowed to about the wave time, with one slot the first finishes at its own cost and the second waits. The metric for a concurrency decision is the wall time; the mean says who waited.

Perplexity and KL are one number seen two ways: PPL = exp(CE) and KL = CE − H(reference). So the dashed line is the reference's own perplexity — exp(H), the floor a perfect model would sit on — and the gap between a series and that line IS its KL. Both 4-bit arms sit within 0.002 of the floor at every size, which is why the KL chart is the one with the resolution.

The smallest request carries only 3 questions (the size is made by one item), so its KL is the thinnest point on the chart; the others carry 60, 135 and 255.

Accuracy needs TWO things held fixed, and both were violated at some point here. (1) The bytes. Every arm replays the bf16 oracle's own prompt (--from-dump), so the KL is between two answers to the same question. It used to be that each arm calibrated its own prompt to the size target, so two arms answering slightly different questions were compared — 40 tokens of prompt difference is enough to move the KL by more than the effect being measured. (2) The context length the arm was STARTED with. vLLM's answers are not invariant to max_model_len: replaying the same bytes with max_tokens 32,768 and then 131,072 moves its mean KL by 1.3e-05 to 3.3e-04 with 0 top-1 flips, because the KV reserve and the block table change which kernels run. A comparison that gives vLLM 32,768 and aiis-clef 131,072 therefore reads a false deficit at the long rungs — it did, and it was withdrawn. Every number on this page is at the same max_tokens, 131,072, for both 4-bit arms.

KL of exactly 0.00e+00 means the two checkpoints returned IDENTICAL answers, not that the arm is perfect. The answers are two-class decisions rounded to four decimals, so when both arms round to the same value the column reads zero and cannot discriminate them. A discriminating accuracy measurement needs questions the model is not confident about; until then, read a zero as "no measurable difference on these questions", never as "zero error".

— means no bf16 arm, so there is no accuracy figure — at 128.1k the bf16 oracle runs out of memory (31.9 of 32.6 GB) and the request fails, measured, not assumed. Nothing in these columns is ever measured against the other 4-bit arm: a KL between two quantised runtimes is a different quantity and would not be comparable with the rows above it. Every number shown is against bf16. “ours vs vLLM” above 1.00× means aiis-clef is faster. KL is the mean over the questions both arms answered; top-1 agreement is 1.000 for both at every size, so no question's preferred answer changed.

How it was measured

Every arm runs alone on the card — the arms cannot be resident at once — 3 rounds each, the running order rotated so a slow minute cannot favour one engine. Latency is measured over HTTP from request to complete answer, not inside the engine, and every figure is the median of the rounds: with three rotated rounds a single slow minute would move a mean by a third and a median not at all. The sizes are TOKEN counts and they are the project's fixed ladder — 779, 8,192, 16,384, 32,768, 65,536, 131,072 — calibrated closed-loop against the arm's own tokenizer, so a run in this window is comparable with a run in the next and nobody has to re-derive a size. (They used to be CHARACTER counts passed as --buckets, which is why older tables carry sizes like 12,526 that no stored command line reproduces.) The condition each arm was started with is printed above: max_tokens from its own /health, and for aiis-clef the attention split count att_keys, because a latency number is only comparable with another measured at the same settings. Accuracy is KL between the answer distributions each arm returned for the same questions, against the bf16 arm's own answers. Generated by deploy/bench/report.py from the harness's output.

READ THE SPREAD BEFORE THE RATIO. The card's own speed moves between windows — measured on identical code at 130.7k tokens, aiis-clef read 11.93 / 12.42 / 13.57 s in three windows hours apart while its within-window spread was 0.2–0.7%. That is a 14% swing, and it is larger than every difference in the table above. Clock pinning is the standard cure and this container refuses it (nvidia-smi -lgc returns Unknown Error), so a ratio here is only meaningful to about ±7%: treat 1.00× as level and anything inside 0.93–1.07× as unproven. The within-window spreads per arm are in the table's source JSONs, and the protocol that reduces the swing is paired rounds — each arm's round measured immediately before or after the other's — which is why the running order rotates.
